# 先生向け出席確認機能 追加仕様

## 位置付け

このドキュメントは、先生が出席対象を設定し、生徒ごとの出席状況を確認する機能について、検討済みの内容と未決定事項をまとめる。

既存の要件では、本人以外の入退室履歴の閲覧と出席・欠席判定を対象外としている。本機能はその方針を変更する追加要件である。ただし、先生へ入退室履歴全体を公開するのではなく、出席確認に必要な情報だけを提供する。

本ドキュメント内の名称、API、DB構造は実装前の設計案であり、未実装である。

## 用語

既存の `attendance_events` は、認証アプリから受信する1回の入室または退出記録を表す。

先生が期間を設定する対象は、既存のイベントと区別して「出席対象」と呼び、コードおよびDBでは `attendance_session` を使用する案とする。

## 利用者と権限

### 先生

- 先生は出席対象を作成できる
- すべての先生が、すべての出席対象を閲覧できる
- すべての先生が、すべての出席対象を編集・中止できる
- 先生は、出席対象ごとに全生徒の出席状況を確認できる
- 先生がシステム管理者を兼ねることを許可する
- 先生であることだけを理由に、管理者向けの利用者管理機能や管理操作履歴へのアクセスを許可しない
- 出席確認に関係しない生徒の入退室履歴は閲覧できない

### システム管理者

- システム管理者であることだけを理由に、出席対象や生徒の出席状況へアクセスできない
- システム管理者向けの利用者管理権限と先生向け権限は分離する
- 先生でもあるシステム管理者は、それぞれの権限に基づいて先生向け機能と管理者向け機能の両方を利用できる

### 生徒

- 従来どおり、自分自身の入退室履歴を確認できる
- 先生向けの出席対象作成、編集、一覧、出席状況確認は利用できない

## 利用者モデル

従来の単一の `role` を廃止し、利用者の種別とシステム管理権限を次のように分離する。

```text
user_type: student | teacher
is_admin: boolean
```

この構造では、`user_type = teacher` かつ `is_admin = true` の利用者を許可する。

既存利用者はすべて `student` へ移行し、従来の `admin` だけを `is_admin = true` とするmigrationを実装済みである。

### 学籍番号

- 生徒の学籍番号は必須とし、既存どおりハイフンなしの数字10桁とする
- 先生は学籍番号を持たない可能性があるため、学籍番号にNULLを許可する
- 生徒には学籍番号が必須であることを、DB制約とアプリケーションのvalidationで保証する
- 学籍番号の一意性は維持する
- 先生アカウントは当面Web利用を主目的とする
- 先生のLCD表示名は任意とし、未入力の場合はNULLを保存する
- 学籍番号がない先生には顔画像登録を提供しない

### 先生アカウントの作成

- システム管理者が利用者アカウントを追加するときに、生徒または先生の利用者種別を選択する
- 利用者作成APIは利用者種別を受け取り、種別に応じて入力を検証する
- 生徒を選択した場合は学籍番号を必須とする
- 先生を選択した場合は学籍番号を任意とし、未入力の場合はNULLを保存する
- 先生アカウントの作成に、先生権限は必要としない
- システム管理者権限の付与方法は既存方針に従い、先生という利用者種別の選択とは分離する

## 出席対象

先生は、少なくとも次の情報を指定して出席対象を作成する。

- 名称
- 授業の開始日時
- 終了日時

対象者を先生が個別指定する機能は設けず、全生徒を対象とする。

### 状態

出席対象には、少なくとも次の状態を持たせる案とする。

- 予定
- 実施中
- 終了
- 中止

出席対象は物理削除せず、中止状態にする。状態をDBへ保存するか、日時から算出するかは実装前に確定する。

### 対象生徒

出席対象ごとの対象生徒は保存せず、全生徒を対象とする。利用者の追加や状態変更によって過去の出席対象に表示される生徒が変化することは許容する。

## 出席判定

出席受付は授業開始10分前から開始する。授業開始20分後までは出席とし、それを超えて出席対象の終了日時より前に入室した場合は遅刻とする。

対象生徒ごとに、受付期間内で最初の入室記録を判定に使用する。

```text
reception_opens_at = attendance_session.starts_at - 10 minutes
late_cutoff_at = attendance_session.starts_at + 20 minutes

出席:
  reception_opens_at <= authenticated_at <= late_cutoff_at

遅刻:
  late_cutoff_at < authenticated_at < attendance_session.ends_at
```

- 判定対象は `event_type = check_in` の入室記録だけとする
- 授業開始20分後と同時刻の入室は出席として扱う
- 終了日時と同時刻の入室は判定対象に含めない
- 受付開始より前の入室記録は判定対象に含めない
- API受信日時の `received_at` ではなく、認証日時の `authenticated_at` を使用する
- 同じ生徒が受付期間内に複数回入室しても、最初の1件だけで判定する
- 退出記録の有無は出席条件に含めない
- 受付開始より前から研究室内にいたことは出席条件に含めない
- 通信障害などで入室記録が遅れて届いても、認証日時が受付期間内なら判定へ反映する
- 未照合の入室記録が後から生徒へ紐付いた場合も、条件を満たせば判定へ反映する

出席結果は、入退室記録から都度計算する案とする。これにより、遅延して到着した記録や後から照合された記録を反映できる。手動修正が必要になった場合は、修正理由と履歴を含む別の仕様を追加する。

### 表示状態

出席状況は、時刻と入室記録に応じて次のように表示する。

| 出席対象の状態 | 期間内の入室 | 表示 |
| --- | --- | --- |
| 開始前 | なし | 未判定 |
| 実施中 | なし | 未登録 |
| 実施中 | 出席時刻内にあり | 出席 |
| 実施中 | 遅刻時間帯にあり | 遅刻 |
| 終了 | なし | 欠席 |
| 終了 | 出席時刻内にあり | 出席 |
| 終了 | 遅刻時間帯にあり | 遅刻 |
| 中止 | 任意 | 中止 |

出席対象の開始前であっても、受付開始後に入室済みの場合は出席と表示する。

## 出席判定の環境変数

大学の運用変更に対応できるよう、受付開始と遅刻判定の閾値は環境変数で設定する。

| 環境変数 | 既定値 | 用途 |
| --- | --- | --- |
| `ATTENDANCE_RECEPTION_OPEN_MINUTES_BEFORE` | `10` | 授業開始の何分前から受付を開始するか |
| `ATTENDANCE_LATE_AFTER_MINUTES` | `20` | 授業開始の何分後を超えたら遅刻にするか |

- 値は0以上の整数とする
- API起動時に検証し、不正な値の場合は起動を失敗させる
- 判定ロジックはAPI側へ集約し、Webアプリが環境変数を直接参照しないようにする
- 環境変数は全出席対象へ共通して適用する
- 環境変数を変更した場合はAPIプロセスの再起動を必要とする
- 環境変数は運用開始後に変更しない前提とし、出席対象ごとに設定値を保存しない
- 環境変数変更時の過去の出席結果への影響は考慮しない

## 先生向け表示

出席対象の一覧または詳細では、少なくとも次の情報を表示する案とする。

- 出席対象の名称
- 開始日時と終了日時
- 状態
- 対象生徒数
- 出席数、欠席数、未判定または未登録の人数
- 遅刻者数
- 生徒名
- 学籍番号
- 出席状態
- 出席の根拠となった期間内の最初の入室時刻

先生には、出席対象の期間外における入退室履歴や、出席判定に不要な退出記録を表示しない。

## データモデル案

```text
attendance_sessions
- id
- title
- starts_at（授業開始日時）
- ends_at
- status
- created_by
- created_at
- updated_at
```

対象は全生徒で固定されているため、出席対象と生徒を関連付ける中間テーブルは設けない。

日時は既存方針に合わせてoffset付きISO 8601文字列で保存し、画面では日本時間で表示する。

## 同時編集

すべての先生が編集できるため、`updated_at` を使った楽観ロックを行う。

更新リクエストには、画面が取得した時点の `updatedAt` を含める。DB更新では、出席対象IDと現在の `updated_at` がリクエストの値に一致することを条件にする。

```sql
UPDATE attendance_sessions
SET
  title = :title,
  starts_at = :startsAt,
  ends_at = :endsAt,
  updated_at = :newUpdatedAt
WHERE id = :id
  AND updated_at = :expectedUpdatedAt;
```

更新件数が0件の場合は、対象の存在を確認する。

- 対象が存在しない場合はNot Foundとして扱う
- 対象が存在する場合は同時更新の競合として、`409 Conflict` と事前定義したアプリケーションエラーを返す

競合時に後勝ちで上書きせず、画面へ最新情報の再取得を求める。

## 監査ログ

既存の `admin_audit_logs` を管理操作専用ではない監査ログへ一般化し、テーブル名を `audit_logs` へ変更する。既存の監査ログは移行時に失わない。

監査ログは、管理操作と出席対象操作を同じテーブルへ記録する。ただし、閲覧APIと認可は用途ごとに分離する。

```text
audit_logs
- id
- actor_user_id
- action
- resource_type
- resource_id
- occurred_at
- changed_fields
- changes
```

- `resource_type` と `resource_id` で操作対象を識別する
- `changed_fields` には変更された項目名を保存する
- `changes` には保存を許可した項目の変更前後をJSONで保存する
- パスワード、パスワードハッシュ、セッショントークン、一時パスワードなどの機密値は保存しない
- 出席対象の更新と監査ログの追加は同じDBトランザクションで行う
- 出席対象の作成と中止も、それぞれの処理と監査ログ追加を同じDBトランザクションで行う

出席対象について、少なくとも次のactionを追加する案とする。

- `attendance_session_created`
- `attendance_session_updated`
- `attendance_session_cancelled`

### 監査ログの閲覧権限

- 先生は出席対象に関する監査ログだけを閲覧できる
- システム管理者は従来の利用者管理に関する監査ログだけを閲覧できる
- 先生権限だけでは管理操作履歴を返さない
- システム管理者権限だけでは出席対象の監査ログを返さない
- 先生とシステム管理者を兼ねる場合は、両方の監査ログをそれぞれの権限に基づいて閲覧できる
- 同じテーブルを利用しても、用途ごとにAPIとRepositoryの検索条件を分ける

## 既存要件への影響

本機能を実装する際は、少なくとも次の既存仕様を更新する必要がある。

- 本人以外の入退室履歴を閲覧できないという要件に、先生向け出席確認の例外を追加する
- 出席・欠席・遅刻判定を対象外としている記述を変更する
- 利用者の役割と認可モデルを変更する
- 学籍番号を全利用者必須としている制約を変更する
- 管理操作専用としている監査ログを汎用化する

## 実装フロー

実装は、利用者・権限基盤、監査ログ、出席対象、出席判定、Web画面の順に進める。後続機能が依存する認証・認可とデータ移行を先に完了させる。

### 1. 既存動作をテストで固定する

変更前に、少なくとも次の既存動作を回帰テストで保護する。

- 一般利用者と管理者のログイン
- 管理者APIの認可
- 管理者による利用者作成
- 未照合入退室イベントの利用者への紐付け
- 本人の入退室履歴取得
- 管理操作監査ログの取得
- 既存DBからのmigration

### 2. 利用者種別と管理者権限を分離する（実装済み）

既存の `role: member | admin` を、次の2つの属性へ移行する。

```text
user_type: student | teacher
is_admin: boolean
```

既存利用者は次のように移行する。

```text
member -> user_type=student, is_admin=false
admin  -> user_type=student, is_admin=true
```

同じmigrationで、先生に対応するため `student_number` をnullableにする。生徒の場合だけ学籍番号を必須にするCHECK制約を設け、学籍番号の一意制約は維持する。

アプリケーションでは次を変更する。

- 認証済み利用者へ `userType` と `isAdmin` を返す
- 管理者middlewareは `isAdmin` を検査する
- 先生middlewareを追加し、`userType === "teacher"` を検査する
- 先生兼管理者は両方の権限を利用できるようにする
- migration testで既存利用者、認証情報、セッション、入退室イベントとの参照が失われないことを確認する

### 3. 管理者による先生アカウント作成に対応する（実装済み）

管理者の利用者作成APIとWeb画面へ、生徒または先生の選択を追加する。

- 生徒を選択した場合は学籍番号を必須にする
- 先生を選択した場合は学籍番号を任意にする
- 先生作成時は未照合入退室イベントの紐付けを行わない
- 利用者一覧と詳細へ利用者種別を表示する
- 利用者一覧で利用者種別を絞り込めるようにする
- 学籍番号を前提とする顔画像登録などの操作は、学籍番号のない先生には提供しない

先生をWeb専用アカウントとする場合は、同じ段階で `lcd_display_name` をnullableにし、先生には入力を求めない。これは先生の入退室記録機能に関する未決定事項を確定してから実施する。

### 4. 監査ログを一般化する

`admin_audit_logs` から `audit_logs` へのmigrationを行う。既存レコードは失わず、次のように変換する。

```text
resource_type = "user"
resource_id   = 旧target_user_id
changes       = NULL
```

- 既存の管理者向け監査ログAPIは維持する
- 管理者向けAPIは利用者管理に関するactionだけを返す
- 出席対象用の監査ログ取得は、先生向けAPIとして別に追加する
- 既存ログの件数と内容を保持するmigration testを追加する

### 5. 出席判定設定を読み込む

API起動時に出席判定用の環境変数を読み込み、0以上の整数であることを検証する。

- 環境変数の解析処理を設定モジュールへ分離する
- 解析済みの設定値を出席判定ユースケースへ依存注入する
- ユースケース内で `process.env` を直接参照しない
- 不正な設定値の場合はAPIの起動を失敗させる

### 6. 出席対象のDBとバックエンドを追加する

`attendance_sessions` テーブルとRepositoryを追加する。予定、受付中、実施中、終了は現在時刻から算出し、自動的な状態更新処理を不要にする案を推奨する。中止だけは `cancelled_at` などで永続化する。

ユースケースは次のように、1ユースケースにつき1ファイルへ分離する。

- `CreateAttendanceSessionUseCase`
- `ListAttendanceSessionsUseCase`
- `GetAttendanceSessionUseCase`
- `UpdateAttendanceSessionUseCase`
- `CancelAttendanceSessionUseCase`

作成、更新、中止と、それぞれに対応する監査ログの追加は同じDBトランザクションで処理する。

### 7. 楽観ロックを実装する

更新と中止のリクエストに、画面が取得した `expectedUpdatedAt` を含める。

- 出席対象IDと `updated_at` が一致する場合だけ更新する
- 更新件数が0件の場合は対象の存在を再確認する
- 対象が存在しない場合はNot Foundとする
- 対象が存在する場合は `409 Conflict` と事前定義した競合エラーを返す
- 競合時は後勝ちで上書きせず、Web画面に最新情報の再取得を求める
- 更新と監査ログ追加を同じトランザクションに含める

### 8. 出席判定を実装する

日時から出席状態を判定する処理は、ユースケースとは別の純粋関数へ分離する。

```text
受付開始より前                         -> 判定対象外
受付開始以上、授業開始20分後以下       -> 出席
授業開始20分後より後、終了日時より前   -> 遅刻
対象記録がなく、終了日時を経過          -> 欠席
```

Repositoryでは、対象となる全生徒と、受付期間内における各生徒の最初の `check_in` を取得する。生徒ごとにSQLを発行するN+1取得は避ける。

出席結果取得は `GetAttendanceSessionResultsUseCase` として実装し、遅延して届いた入室イベントと、後から利用者へ紐付いた入室イベントを都度反映する。

### 9. 先生向けAPIを追加する

APIは次の構成案とする。

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/attendance-sessions` | 出席対象一覧 |
| `POST` | `/api/v1/attendance-sessions` | 出席対象作成 |
| `GET` | `/api/v1/attendance-sessions/:id` | 出席対象詳細 |
| `PATCH` | `/api/v1/attendance-sessions/:id` | 出席対象更新 |
| `POST` | `/api/v1/attendance-sessions/:id/cancel` | 出席対象中止 |
| `GET` | `/api/v1/attendance-sessions/:id/results` | 生徒別出席結果 |
| `GET` | `/api/v1/attendance-sessions/:id/audit-logs` | 出席対象の変更履歴 |

- すべてCookieセッションと先生権限で保護する
- 変更系APIにはOrigin検証を適用する
- RouteはvalidationとHTTPへの変換に限定する
- 想定内のエラーは `AppError` の派生例外とし、JSONへの変換は `app.onError` へ集約する

### 10. 先生向けWeb画面を追加する

バックエンドの契約を確定してから、次の順で画面を追加する。

1. 先生用ナビゲーションとルーティング
2. 出席対象一覧
3. 出席対象の作成・編集・中止
4. 楽観ロック競合時のエラー表示と再読み込み
5. 生徒別出席結果と集計
6. 出席対象の変更履歴

先生兼管理者には先生用と管理者用の両方のナビゲーションを表示する。フロントエンドの表示制御は補助とし、正式な認可はAPIで行う。

### 11. テストと移行確認を行う

少なくとも次のケースをテストする。

- 生徒、先生、管理者、先生兼管理者の認可
- 生徒と先生を作成するときの条件付きvalidation
- 受付開始10分前と同時刻の入室
- 授業開始20分後と同時刻の入室
- 授業開始20分後を超えた入室
- 終了日時と同時刻の入室
- 複数の入室記録がある場合に最初の記録を使用すること
- 遅延して届いた入室イベント
- 未照合イベントの後日紐付け
- 同じ `updatedAt` を使った同時更新
- 出席対象の更新失敗時に監査ログだけが残らないこと
- 既存利用者、入退室イベント、セッション、監査ログを失わないmigration
