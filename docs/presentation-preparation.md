# Smart Gate Web・API 発表準備用資料

## この資料について

この資料は、発表内容を指定するものではなく、発表担当者がSmart GateのWeb・API部分を理解し、自分で発表内容を組み立てるための参考資料である。

Web開発に詳しくない人でも全体像をつかめるよう、細かなAPI一覧やコードの説明は省いている。

---

## 1. Smart GateのWeb・APIは何をしているか

Smart Gateは、研究室の入室・退出を記録するシステムである。

全体は大きく次のように分かれる。

```text
利用者・管理者
      │
      ▼
Webアプリ
      │
      ▼
API
   │       │
   ▼       ▼
SQLite   Python認証アプリ
          顔・カード認証
```

### それぞれの役割

- **Webアプリ**  
  利用者や管理者がブラウザで操作する画面。

- **API**  
  Web画面や認証アプリから要求を受け、認証・確認・保存などの処理を行う。

- **SQLite**  
  利用者情報、入退室履歴、ログイン情報、監査ログなどを保存する。

- **Python認証アプリ**  
  顔認証・カード認証そのものを行う。Web・APIとは別システム。

つまり、Web・API側は**認証そのものではなく、認証結果の保存・表示・管理**を担当している。

---

## 2. Webアプリでできること

### 一般利用者

- ログイン
- 月ごとの入退室履歴をカレンダーで確認
- 日別の入室・退出時刻を確認
- 認証方法を確認
- 参考滞在時間を確認
- パスワード変更

### 管理者

上記に加えて、

- 利用者の検索・登録・編集
- 顔認証用画像の登録
- 利用者の有効化・無効化
- ロック解除
- パスワード再発行
- セッション失効
- 管理操作の監査ログ確認

ができる。

現在、管理者が他人の入退室履歴を見る機能はない。

---

## 3. APIとは何か

APIは、Web画面や認証アプリと、データベースの間に入る処理の入口である。

例えば履歴を見るときは、

```text
Web画面
  ↓
APIへ「この月の履歴が欲しい」と要求
  ↓
APIがSQLiteから取得
  ↓
Web画面へ返す
```

という流れになる。

Web画面がSQLiteを直接操作するわけではない。

APIを間に置くことで、

- ログイン済みか
- 管理者権限があるか
- 送られたデータが正しい形式か

などをまとめて確認できる。

---

## 4. 入退室イベントが保存される流れ

顔認証またはカード認証が成功すると、Python認証アプリからAPIへ認証結果が送られる。

主な情報は、

- イベントID
- 学籍番号
- 入室または退出
- 認証方法
- 認証時刻
- 端末ID

である。

流れは次のようになる。

```text
顔・カード認証
      ↓
Python認証アプリ
      ↓
入退室イベント
      ↓
API
  ・送信元を確認
  ・入力形式を確認
  ・利用者を確認
      ↓
SQLiteへ保存
```

---

## 5. 実装上の重要な工夫

### 同じイベントを二重登録しない

通信が途中で切れると、認証アプリが同じイベントを再送する可能性がある。

そのため、イベントごとに一意な `eventId` を持たせている。

同じ `eventId` が再送されても、新しい記録は追加しない。

この性質を**冪等性**という。

簡単に言えば、

> 同じデータを再送しても記録が2件に増えない仕組み

である。

### 未登録利用者のイベントも捨てない

イベントが届いた時点で、その学籍番号の利用者がWeb側に登録されていなくても、イベントは保存する。

後から同じ学籍番号の利用者が登録されると、自動で紐付ける。

```text
イベント受信
   ↓
利用者が未登録
   ↓
未照合のまま保存
   ↓
後から利用者登録
   ↓
自動で紐付け
```

### 不足した記録を勝手に補わない

入室だけ記録されている場合は「退出記録不足」、退出だけの場合は「入室記録不足」として扱う。

存在しないイベントを推測して追加することはしない。

そのため、表示される滞在時間は**参考値**である。

---

## 6. ログインとセキュリティ

主な仕組みは次のとおり。

- パスワードは平文で保存せず、Argon2idでハッシュ化
- ログイン状態はCookieで管理
- 管理者向けAPIでは毎回管理者権限を確認
- ログイン失敗が続くと一時的にロック
- 認証装置からのイベント送信はBearer tokenで保護
- 管理者の操作は監査ログへ記録

画面上で管理機能を隠すだけでなく、API側でも権限を確認している。

---

## 7. 顔画像の扱い

管理画面から登録された顔画像は、APIを経由してPython認証アプリへ送る。

```text
管理者
  ↓
Web画面
  ↓
API
  ↓
Python認証アプリ
```

Web・API側では、

- 顔画像本体をSQLiteへ保存しない
- ファイルとしても保存しない
- SQLiteには登録枚数だけ保存する

という設計になっている。

顔画像から作られた特徴量の保存はPython認証アプリ側の担当である。

---

## 8. 使用している主な技術

| 技術 | 役割 |
| --- | --- |
| React | ブラウザ画面を作る |
| TypeScript | データの型を定義し、実装ミスを減らす |
| Hono | APIを作る |
| Zod | APIへ送られた値を検証する |
| Drizzle ORM | TypeScriptからSQLiteを操作する |
| SQLite | データを保存する |
| Argon2id | パスワードを安全に保存する |

細かな特徴まで覚える必要はなく、

```text
React ＝ 画面
Hono ＝ API
SQLite ＝ データ保存
Pythonアプリ ＝ 顔・カード認証
```

という関係を理解しておけばよい。

## 9. 現時点で未完了のこと

2026年9月12日時点では、主に次が未完了または未確定である。

- Raspberry Pi起動時の自動起動
- API異常終了時の自動再起動
- SQLiteのバックアップ
- 本番HTTPS設定
- Raspberry Pi実機への正式な配置手順
- ブラウザ操作を通したUI自動テスト

また、二重登録防止は**同じ `eventId` の再送**を対象としている。

異なる `eventId` で同じ内容が届いた場合まで、自動で重複と判定する仕様ではない。

## 10. 誤解しやすい点

| 誤解 | 実際 |
| --- | --- |
| Webアプリが顔認証する | 顔認証はPythonアプリが行う |
| 顔画像をSQLiteへ保存する | APIはPython側へ転送するだけ |
| 管理者は全員の履歴を見られる | 現在の履歴機能は本人向け |
| 滞在時間は正確な在室時間 | 入退室記録から求めた参考値 |
| 再起動すれば自動復旧する | DBは残るが自動起動・再起動は未実装 |

## 11. 最低限知っておきたい用語

| 用語 | 意味 |
| --- | --- |
| フロントエンド | ブラウザで利用者が操作する部分 |
| API | 画面や別システムから要求を受ける入口 |
| DB | データを保存・検索する仕組み |
| Cookie | ブラウザがログイン状態を伝える仕組み |
| セッション | ログイン状態を管理する仕組み |
| Bearer token | 正規の送信元であることを示す秘密情報 |
| ハッシュ化 | 元のパスワードなどをそのまま保存しない変換 |
| トランザクション | 複数のDB操作をまとめて成功・失敗させる仕組み |
| 冪等性 | 同じ要求を繰り返しても結果が重複しない性質 |
| 監査ログ | 誰がいつ何を操作したかを残す記録 |

## 12. 詳細を確認したい場合

より詳しい実装を確認する場合は、次の場所を参照する。

| 内容 | 主な場所 |
| --- | --- |
| Webアプリ | `apps/web/src/` |
| 入退室履歴 | `apps/web/src/features/history/` |
| 利用者管理 | `apps/web/src/features/admin/users/` |
| API | `apps/api/src/routes/` |
| 業務処理 | `apps/api/src/services/` |
| SQLite操作 | `apps/api/src/repositories/` |
| DB構造 | `apps/api/src/db/` |
| 未完了項目 | `TASKS.md` |

コードを読むこと自体は必須ではない。

発表準備中に「この機能はどこまで実装されているのか」を確認したい場合の参照先として使う。
